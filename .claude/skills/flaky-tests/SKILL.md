# Flaky-тесты: от подозрения до доказанного фикса

Задача — **доказанная причина и фикс, который устраняет её, а не симптом**. Зелёный прогон сам по себе ничего
не доказывает. Комментарии в коде («passes ~40%», «FIX: …») и чужие «ожидаемые решения» — гипотезы, не данные.

## Жёсткие правила (стоп-точки)

- **Без маскировки.** Запрещено как фикс: `sleep`/`waitForTimeout`/фиксированные задержки, увеличение таймаутов,
  ретраи (в коде или конфиге), ослабление ассерта (проверять меньше, чем проверялось), `skip`/`fixme`, подавление
  линтера. Если такое предлагается (в т.ч. самим Claude) — записать в журнал промптов как попытку маскировки.
- **Аппрув после Этапа 2.** Код теста/продукта не меняется до явного «да» пользователя на план фиксов.
- **Эскалация после 2 неудачных итераций** фикса одного теста — стоп, собранные данные пользователю.
- **Без коммитов и пушей** без запроса. Секреты (`.env`, storage state, токены) не попадают в артефакты и `meta.json`.
- Эксперименты принудительного воспроизведения — через шаблоны скилла и локальный патч из `.flaky/`
  (или разовые файлы в `repro/` артефактов), не в основной код.
- Любое отклонение от утверждённого плана — сначала согласовать.

## Шаг 0. Развернуть скилл в проекте

В целевом репо работа раскладывается на три слоя, содержимое между ними не дублируется
(подробно и шаблоны — `references/reporting.md` → «Развёртывание в проекте»):

| Слой | Где | Что |
|---|---|---|
| Скилл | `.claude/skills/flaky-tests/` | методика, скрипты, шаблоны — одинаковы для любого проекта |
| Обвязка | `.flaky/` | `profile.md` (команды, параметры, конвенции) + `apply-repro.patch` (подключение repro к фикстуре `page`) |
| Отчёт | `deliverables/flaky/` (или папка из профиля) | `README.md`, `1-research` … `5-reflection.md`, `runs/` — что нашли и доказали |

Если `.flaky/profile.md` уже есть — прочитать и работать по нему. Если нет:
1. Скилл только глобальный → предложить скопировать его в `.claude/skills/flaky-tests/` репо (источник истины —
   копия в репо, глобальная синхронизируется копированием).
2. Собрать `.flaky/profile.md` из `package.json`/`playwright.config.*`/CI/`CLAUDE.md`/README по шаблону и
   **показать пользователю на подтверждение**: версия Playwright и проекты конфига, команды запуска/фильтра/
   повтора, подготовка окружения, cold (нужен ли гейт), repro-параметры, команда снимка окружения, конвенции
   архитектуры (где локаторы, где ассерты, что запрещено линтером), lint/typecheck, папка артефактов, порог N,
   регэкспы шума. Определения команд живут только в профиле; отчёты на него ссылаются.
3. Сгенерировать `.flaky/apply-repro.patch` под фикстуру проекта и проверить: патч применяется, typecheck/lint
   зелёные, файл возвращён.
4. Создать скелет отчёта (`README.md`, `1-research.md` … `5-reflection.md`, `runs/.gitkeep`) с заголовками
   из шаблонов.

Для другого раннера методика (этапы, критерии, матрица) применима, но команды, шаблоны repro и cold придётся
подобрать по документации раннера (через Context7, если доступен).

## Этапы

Переход дальше — только при выполненном критерии выхода. Журнал промптов (`5-reflection.md` → «Журнал промптов»)
ведётся с первого этапа.

### Этап 1 — Инвестигация
1. **Критерии** — `references/measurement.md`: определение флейка, классы исходов, правило трёх, критерий «починен».
2. **Статика** → `1-research.md` §2 «Анализ кода»: весь тестовый код + PO/helpers + фикстуры + конфиг + CI по чек-листу
   `references/root-cause.md`. Таблица «ID риска / файл:строка / антипаттерн / механизм /
   риск / активный или латентный». Проверь, не противоречат ли комментарии и документация коду.
3. **Матрица прогонов** → `1-research.md` §3 «Прогоны «до»»: волнами, `references/measurement.md`. Каждый прогон — через
   `scripts/run-condition.mjs`, статистика — `scripts/flaky-stats.mjs`. Перед волной 1 замерь длительность
   одного прогона и оцени время волн.
4. **Pass vs fail** → `1-research.md` §4: по каждому флейку пара артефактов (trace/лог/скрин) одного успешного и
   одного упавшего прогона, различия по шагам, сети, URL, таймингам.

Выход: у каждого теста класс; у каждого флейка частота по условиям и пара pass/fail; карта рисков готова.

### Этап 2 — План
1. **Гипотезы** → `2-plan.md` §1: в порядке вероятности, у каждой — что подтверждает, что опровергает,
   минимальный эксперимент. Сверить с данными Этапа 1.
2. **Принудительное воспроизведение** (`references/root-cause.md`): для главной гипотезы сделать флейк
   воспроизводимым ~100% → «при условии X тест падает N/N» = гипотеза доказана. Не воспроизводится — понизить
   гипотезу, взять следующую. Repro переиспользуется в Этапах 3–4.
3. **Вердикт «тест или продукт»** → `2-plan.md` §3 (логика) и `3-fix.md` §2 (вывод). Дефект теста → чиним тест. Дефект/неопределённость
   продукта или данных → ожидание теста меняется на реально гарантированное поведение + баг/вопрос команде.
4. **План фиксов** → `2-plan.md` §4: тест / доказанная причина / что меняем / новые методы / риск для других тестов. Если есть
   «эталонное» решение — сверить и указать, где его можно улучшить.
5. **Сверка с архитектурой** по профилю: конвенции, переиспользование фикстур, линтер, нет маскировки,
   изменённые общие методы не ломают другие тесты (найти всех потребителей).
6. **Аппрув пользователя.**

Выход: причина каждого флейка доказана repro (или явно помечена недоказанной с объяснением), вердикт, план, аппрув.

### Этап 3 — Имплементация
1. Фиксы по плану (шаблон «Предложение исправления» в `references/reporting.md`).
2. Каждый фикс проверить на его repro: при принудительном условии тест **проходит**.
3. `3-fix.md` §1 — что изменено и почему это устраняет причину; §3 — общий паттерн, если флейков несколько.
4. lint + typecheck из профиля зелёные.

### Этап 4 — Верификация
1. **До/после чередованием в одной сессии**: код «до» — в `git worktree` на исходном коммите, «после» —
   рабочая ветка; блоки по 10: before → after → before → after…, пока не наберётся ≥ N «после» (порог
   профиля, по умолчанию 30) и ≥ 20 «до» в каждом обязательном условии. `--block` в `run-condition.mjs`.
2. `flaky-stats.mjs` по всем before+after → `4-verify.md` §2 (`--out`; до/после, отметка «починен», метаданные, совпадение
   снимков окружения).
3. **Негативная проверка**: сломать защищаемое поведение (или включить repro для «старой» ошибки) → тест
   падает по правильной причине с понятным сообщением.
4. Полный основной набор + lint + typecheck зелёные.
5. Не прошёл порог → назад на Этап 2 с новыми данными (максимум 2 итерации, потом эскалация).
6. `4-verify.md` §5 «Трассировка»: риск → гипотеза → доказательство → вердикт → фикс → результат. `5-reflection.md`
   по журналу промптов: что сделано хорошо/плохо, попытки маскировки, что поменять в промптах.

Выход: исправленные тесты «починены» по критерию (или эскалированы), проверки зелёные, отчёты готовы.

## Скрипты и шаблоны

`<skill>` — папка скилла: `.claude/skills/flaky-tests` в репо (проектный скилл, если он там лежит) или
`~/.claude/skills/flaky-tests`. Команды запускаются из корня целевого репо. Копии скриптов в папку артефактов
не кладутся: ссылки в отчётах ведут на скилл, специфика проекта — параметры в профиле.

```bash
# один прогон условия: отчёт + лог + meta.json (commit, dirty, env, версии, время, exit, снимок окружения)
node <skill>/scripts/run-condition.mjs <phase> <condition> [--block N] \
  [--format json|junit] [--version-cmd CMD] [--browser-cmd CMD] [--snapshot-cmd CMD] [--meta-env BASE_URL] \
  -- <команда раннера из профиля, {report} = путь отчёта>

# статистика: тест × условие, целевые падения vs шум, класс, до/после, порог
node <skill>/scripts/flaky-stats.mjs [--threshold 30] [--noise setup,network] \
  [--setup-re RE] [--network-re RE] [--grep RE] [--out stats.md] <phase>:<condition>=<report> ...

# снимок списка в порядке SSR (для --snapshot-cmd и гипотез о порядке данных; нужен Playwright в репо)
node <skill>/scripts/list-snapshot.mjs --item SEL --field SEL [--field SEL] [--repeat K] [--gate-env VAR] \
  <label>=<path без ведущего /> ...
```

Вход `flaky-stats` — Playwright JSON или JUnit XML. Сигнатуры: `setup` (по сообщению/упавшему шагу, не по
стеку), `network`, `timeout`, `assertion`, `other`; code frame исходника из классификации исключается.

Шаблоны — `templates/playwright/`, параметризуются env, в код проекта не копируются:
- `repro-conditions.ts` — условия repro (`REPRO_CONDITION=cpu|request-delay|throttled|gate`); подключаются
  локальным патчем фикстуры `page`, патч проекта — `.flaky/apply-repro.patch`;
- `cold.config.ts` — условие cold для любого проекта основного конфига (за гейтом стенда — вместе с `gate`).

Подробности — в `references/measurement.md` (cold, throttled) и `references/root-cause.md` (repro).

## Справочники

- `references/measurement.md` — что мерить и как: определения, классы, правило трёх, «починен», команды
  Playwright, матрица условий, волны, чередование до/после
- `references/root-cause.md` — где искать причину: чек-лист антипаттернов (+ замены для Playwright),
  принудительное воспроизведение, условия `REPRO_CONDITION`
- `references/reporting.md` — шаблоны промптов; развёртывание в проекте: `.flaky/profile.md`, патч,
  скелет отчёта (README, 1-research … 5-reflection)
- `templates/playwright/` — repro-условия и cold-конфиг
