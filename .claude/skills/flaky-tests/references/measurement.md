# Измерение: критерии и матрица прогонов

Playwright Test (JS/TS), проверено на 1.63.

## Определение

**Flaky** = тот же коммит, то же окружение, тот же тест → разные исходы (pass и fail) **по одной и той же
целевой причине**. Падения из-за setup (логин, подготовка данных, storage state) и сети считаются **шумом
окружения** и учитываются отдельно (`flaky-stats --noise`).

Источник класса — только прогоны. Комментарии в коде, README, история «оно всегда так» — гипотезы.

## Классы (N прогонов без ретраев)

| Исход | Класс | Действие |
|---|---|---|
| N/N pass | `stable-pass` — стабилен **или латентный** | стресс-условия (волна 3) |
| 0/N pass (по целевой причине) | `always-fail` — детерминированное падение, **не flaky** | разбор как обычного падения |
| есть pass и fail (целевая причина) | `FLAKY` | гипотезы → repro → фикс |
| падения только из-за шума | `stable-pass (env noise)` / `noise-only` | в отчёт про окружение, тест не чиним |

Латентный тест — проходит сейчас, но содержит антипаттерн, который сломается при изменении данных, сети,
окружения. Его ловят статикой (Этап 1.2) и стресс-условиями (волна 3); класс подтверждается, если стресс-условие
даёт падения.

## Правило трёх

0 падений из N независимых прогонов → реальная частота падений с 95% уверенностью **не выше ≈ 3/N**.

| N чистых прогонов | Верхняя граница частоты |
|---|---|
| 10 | ~30% |
| 20 | ~15% |
| 30 | ~10% |
| 100 | ~3% |

Отсюда: обнаружение — 20 повторов на условие, подтверждение фикса — 30 (или порог профиля). «Прошло 10 раз» —
не доказательство стабильности теста, который падал в 13% случаев.

Сравнение «до/после» осмысленно, только если частота «до» заметно выше границы «после»: при частоте до 5%
и 30 прогонах после разница статистически не видна — нужно больше прогонов или repro-условие, которое поднимает
частоту «до» к ~100%.

## Критерий «починен»

Все три одновременно:
1. **0 целевых падений из ≥ N** (порог профиля, по умолчанию 30) «после» в каждом обязательном условии
   (`flaky-stats` → «✅ fixed»).
2. Тест **проходит при принудительном воспроизведении** причины (repro из Этапа 2).
3. Тест **падает в негативной проверке** — когда защищаемое поведение реально сломано — с понятным сообщением.

Пункт 1 без 2 — возможно, повезло со стендом. Без 3 — тест мог стать неспособным упасть.

## Команды Playwright

| Что | Как |
|---|---|
| Повтор N раз | `--repeat-each N` |
| Без ретраев | `--retries=0` (переопределяет `retries` из конфига, в т.ч. `process.env.CI ? n : 0`) |
| Воркеры | `--workers=1` / `--workers=4` / `--workers=50%` |
| Один тест | `--grep "ID:"` (якорь на ID, чтобы не зацепить похожие названия), или `file.spec.ts:LINE` |
| Проект | `--project=<name>`; зависимости проекта (setup) запускаются автоматически, `--no-deps` — без них |
| Отчёт | `--reporter=list,json` + env `PLAYWRIGHT_JSON_OUTPUT_NAME` (ставит `run-condition.mjs`); JUnit: `--reporter=list,junit` + `PLAYWRIGHT_JUNIT_OUTPUT_NAME`, `--format junit` |
| Trace | `--trace retain-on-failure` (в конфиге часто `on-first-retry` → при `--retries=0` trace **не пишется вообще**) |
| Встроенный флейк-детектор | `--retries=2`: тест, прошедший на ретрае, получает статус `flaky`; `--fail-on-flaky-tests` |
| Версии | runner: `npx playwright --version`; браузер: `node -e "require('@playwright/test').chromium.launch().then(async b=>{console.log('chromium '+b.version());await b.close()})"` |

Пример условия base:
```bash
node <skill>/scripts/run-condition.mjs before base \
  --version-cmd "npx playwright --version" --browser-cmd "<браузер, см. выше>" \
  -- npx playwright test --project=<p> --repeat-each 20 --workers=1 --retries=0 \
     --reporter=list,json --trace retain-on-failure
```
Артефакты упавших (trace.zip, скрин, error-context.md) — в `test-results/`; каждый прогон его перезаписывает →
нужные trace копировать в `traces/` **сразу после прогона** (или `--output <dir>` на условие).

## Матрица прогонов

Все прогоны: **без ретраев**, машиночитаемый отчёт, артефакты (trace/скрин/лог) только для упавших,
через `run-condition.mjs` (иначе нет `_meta` и сравнение до/после не к чему привязать).

| # | Условие | Что меняем | Что ловит |
|---|---|---|---|
| 1 | `base` | 1 воркер, N повторов | базовая частота |
| 2 | `parallel` | несколько воркеров (≈ число ядер / CI-значение) | конкуренция за CPU, общие данные между воркерами |
| 3 | `isolated` | тест один (фильтр по имени) vs весь файл/набор | зависимость от порядка, утечка состояния между тестами |
| 4 | `cold` | без сохранённой сессии/кэша (vs warm = base) | тайминг гидрации/кэша, зависимость от storage state |
| 5 | `throttled` | CPU ×4–6 + медленная сеть | латентные гонки ожиданий; заменяет «медленный CI» |
| 6 | `retries` | ретраи раннера включены | встроенная пометка flaky раннера — только как доп. подтверждение |
| 7 | `env-B` | другое окружение/хост/локаль | захардкоженные значения, зависимость от данных стенда |

Опционально: `shuffle` (случайный порядок), `ci` (повторные CI-запуски — другое железо).

Как включить условия в Playwright:
- **parallel**: `--workers=4`; при `fullyParallel: false` тесты одного файла всё равно идут в одном воркере
  последовательно — для конкуренции за CPU дополнительно `--fully-parallel`.
- **cold vs warm**: warm = проект со `storageState`. Cold — шаблон `templates/playwright/cold.config.ts`:
  берёт проект основного конфига (`FLAKY_PROJECT`, по умолчанию `flaky`), ставит пустой `storageState`, убирает
  зависимости от setup; пути `testDir`/`outputDir` пересчитывает от корня репо.
  ```bash
  FLAKY_PROJECT=<p> npx playwright test -c <skill>/templates/playwright/cold.config.ts --project=flaky-cold ...
  ```
  Если стенд требует cookie гейта даже анониму (session link и т.п.) — дополнительно repro-патч и
  `REPRO_CONDITION=gate REPRO_GATE_ENV=<имя env-переменной с URL гейта>` (`root-cause.md`): каждый тест сначала
  открывает гейт в чистом контексте, без логина. Конфиг основного репо должен сам грузить `.env`
  (как правило, `import 'dotenv/config'`).
- **throttled** (только Chromium): `REPRO_CONDITION=throttled` (CPU ×4 + ~Slow 3G через CDP, до `goto`),
  подключение — как repro (`root-cause.md`).

## Волны (не гонять всю матрицу сразу)

- **Волна 1:** условие 1 для всех подозреваемых тестов (20 повторов).
- **Волна 2:** условия 2–4 (+6) — только для тестов, которые в волне 1 флейкают или вызывают подозрение по статике.
- **Волна 3:** условие 5 (и 7) — для тех, кто прошёл N/N (кандидаты в латентные).

## Оценка времени

Перед волной 1: один прогон теста (`--repeat-each 1`) → длительность `t`. Волна ≈ `t × повторы × тесты × условия /
воркеры` + setup. Записать в `1-research.md` («Оценка времени») до запуска, после — фактическое время.

## Именование

`runs/<phase>/<YYYY-MM-DD>_<condition>[_<block>].json` — **один файл на прогон**, meta в ключе `_meta` (для JUnit XML —
соседний `.meta.json`). Лог раннера — только у упавших прогонов, в `runs/_local/<phase>/` (git-ignored); trace.zip и
прочие тяжёлые/секретные артефакты — тоже в `runs/_local/`. Сводка — один `runs/stats.md`
(`flaky-stats --out runs/stats.md runs/`: phase/condition берутся из `_meta`, блоки суммируются).
`phase` = `before` / `after` / `repro-*`; `block` — номер блока при чередовании до/после.

## Чередование до/после (Этап 4)

Стенд может меняться между прогонами — поэтому «до» и «после» в одной сессии, блоками:
```
git worktree add ../<repo>-before <исходный коммит>
before:1 → after:1 → before:2 → after:2 → …   (по 10 повторов в блоке)
```
Пока не набрано ≥ N «после» и ≥ 20 «до» в каждом обязательном условии. Снимок окружения
(`--snapshot-cmd`) в каждом блоке; `flaky-stats` предупредит, если он менялся.
