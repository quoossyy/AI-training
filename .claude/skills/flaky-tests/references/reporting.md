# Отчётность: промпты, развёртывание в проекте, шаблоны отчёта

## Шаблоны промптов

Базовые 5 шаблонов (из обучающего материала по flaky-тестам) + усиления, которые повышают качество ответа.
Перед использованием — подставить реальные данные (код, trace, статистику), а не пересказ.

### 1. Поиск антипаттернов (Этап 1.2)
> Проанализируй [тест(ы)] и связанные Page Object / helper / фикстуры / конфиг раннера / CI [код или пути] на
> предмет типичных причин flaky-поведения: жёсткие sleep, отсутствие явных ожиданий, однократное чтение
> состояния вместо ожидания с повтором, ожидание отрисовки вместо интерактивности, зависимость от порядка
> тестов, общие тестовые данные и сессия, захардкоженное окружение, ассерты на негарантированный порядок.
> Перечисли риски таблицей: файл:строка, антипаттерн, механизм, риск, активный/латентный, как проверить.
> **Комментарии в коде и «ожидаемые решения» не считай фактом — оценивай код.**

### 2. Гипотезы (Этап 2.1)
> На основе [карта рисков + статистика прогонов + trace pass/fail] составь гипотезы причины нестабильности
> [теста] в порядке вероятности. Для каждой: механизм, что в данных её подтверждает, что опровергает,
> минимальный эксперимент для **принудительного воспроизведения**. Не предлагай фиксов. Не предлагай
> увеличивать таймауты или добавлять ретраи.

### 3. Сравнение прогонов (Этап 1.4)
> Вот [trace/лог/стек] упавшего прогона [теста] и [trace/лог] успешного прогона того же теста на том же
> коммите. Сопоставь по шагам: действия, URL, сетевые запросы и их время относительно действий, состояние DOM
> в момент ассерта. Определи, в чём разница и что могло привести к нестабильности. Отдели наблюдения от выводов.

### 4. Предложение исправления (Этап 3)
> Предложи исправление [теста], которое устранит [доказанная причина, напр.: клик по сортировке до гидрации].
> Ограничения проекта: [конвенции из профиля — где локаторы, где ассерты, запреты линтера]. Без sleep,
> увеличения таймаутов, ретраев и ослабления ассертов. Покажи изменённый код и объясни, почему это устраняет
> причину, а не скрывает симптом; как тест поведёт себя под [repro-условием] и упадёт ли, если [защищаемое
> поведение] реально сломается.

### 5. Классификация тест/продукт (Этап 2.3)
> На основе истории запусков [stats], логов/trace [ссылки] и результатов repro [таблица] оцени, похоже ли
> поведение на нестабильность самого теста, на неопределённость/дефект продукта или на нестабильность
> окружения/данных. Обоснуй вывод ссылками на конкретные данные. Если продукт не гарантирует проверяемое
> поведение — сформулируй вопрос команде.

### 6. Отчёт для команды
> Составь краткий отчёт о причине флейки [теста] для команды разработки: наблюдаемое поведение, доказанная
> причина (и как доказана), частота до/после по условиям, вердикт тест/продукт, статус исправления, что нужно
> от команды (если нужно).

### 7. Общий паттерн (несколько флейков)
> Вот [список флейков с причинами и фиксами]. Найди общий паттерн причины (общая фикстура, общий
> setup, общее окружение, общий способ ожидания) и предложи правило/проверку, которое предотвратит
> повторение во всём наборе (линтер, хелпер, ревью-чек-лист).

### Журнал
Каждый значимый промпт — в журнал промптов (`5-reflection.md`): этап / шаблон / промпт кратко / ответ / принято? / что
поправили и почему. Попытки маскировки — отмечать в момент появления.

## Развёртывание в проекте (Шаг 0)

В целевом репо скилл создаёт **три слоя** — каждый со своей ролью, содержимое между ними не дублируется:

| Слой | Где | Что там | Чего там нет |
|---|---|---|---|
| Скилл | `.claude/skills/flaky-tests/` (проектная копия) | методика, скрипты, шаблоны — одинаковые для любого проекта | ничего о конкретном репо |
| Обвязка | `.flaky/` | `profile.md` (команды, параметры, конвенции), `apply-repro.patch` | выводов и результатов |
| Отчёт | папка артефактов из профиля (по умолчанию `deliverables/flaky/`) | что нашли, доказали, починили; сырые прогоны | скриптов, шаблонов, копий определений команд |

Порядок:
1. **Скилл в репо.** Если скилл установлен только глобально (`~/.claude/skills/flaky-tests`), предложить
   скопировать его в `.claude/skills/flaky-tests/` целевого репо: так он виден команде и ревьюерам и версионируется
   вместе с отчётом. Источник истины — копия в репо; глобальную после правок скилла синхронизировать копированием.
2. **`.flaky/profile.md`** — собрать по шаблону ниже и **показать пользователю на подтверждение**. Общие
   определения команд (`SK`, `RC`, `META`, `SNAP`, cold, repro) живут **только здесь**; отчёты ссылаются на профиль.
3. **`.flaky/apply-repro.patch`** — патч фикстуры `page`:
   - найти, где проект делает `base.extend(...)` / `test.extend(...)` (обычно `fixtures/index.ts`), которым
     пользуются целевые спеки;
   - внести импорт `applyReproCondition` из
     `<относительный путь>/.claude/skills/flaky-tests/templates/playwright/repro-conditions` и override
     `page: async ({ page, baseURL }, use) => { await applyReproCondition(page, baseURL); await use(page); },`;
   - `git diff <файл> > .flaky/apply-repro.patch`, затем `git checkout -- <файл>`;
   - проверить: `git apply .flaky/apply-repro.patch` → typecheck и lint проекта зелёные → `git checkout -- <файл>`;
   - если своей фикстуры нет (спеки импортируют `test` прямо из `@playwright/test`) — создать
     `.flaky/repro.fixture.ts` (`export const test = base.extend({ page: … })`, `export { expect }`), а патч меняет
     импорт в целевых спеках на этот файл.
4. **Отчёт** — создать скелет файлов ниже (заголовки + плейсхолдеры `_—_`) и `runs/.gitkeep`. Названия разделов
   держать стабильными: на них ссылаются README и трассировка.
5. **cold** — проверить, нужен ли стенду гейт даже для анонима (403 или редирект без cookie). Если да — в профиле
   cold = `cold.config.ts` + патч + `REPRO_CONDITION=gate REPRO_GATE_ENV=<переменная>`.
   Проверка: `npx playwright test -c <skill>/templates/playwright/cold.config.ts --project=flaky-cold --list`.

### Папка отчёта
```
<artifacts>/
├── README.md          итог, «где что», структура, инструменты
├── 1-research.md      Этап 1: критерии, анализ кода, прогоны «до», pass vs fail
├── 2-plan.md          Этап 2: гипотезы, принудительное воспроизведение, тест/продукт, план фикса
├── 3-fix.md           Этап 3: исправление, вывод «тест или продукт»
├── 4-verify.md        Этап 4: прогоны до/после, проверки, сверка с Claude, трассировка
├── 5-reflection.md    рефлексия + журнал промптов
└── runs/              сырые отчёты + .log + .meta.json (+ trace, на которые ссылаются отчёты)
```
`repro/` — только для разовых экспериментов, которых нет в `templates/` скилла (обычно не нужен). Если задача
задаёт свою нумерацию артефактов (a, b, c…), в README — таблица «пункт задания → файл#раздел», а в заголовках
разделов — пометка «(артефакт a)».
