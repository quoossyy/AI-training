# Поиск причины: антипаттерны и принудительное воспроизведение

## Чек-лист антипаттернов (Этап 1.2)

Охват — не только упавший тест: весь тестовый код, PO/helpers, фикстуры, конфиг раннера, CI. Флейк часто живёт
в общей инфраструктуре.

### Синхронизация (ожидания)
- Фиксированные задержки (`waitForTimeout`, `sleep`) — гадание о времени.
- Однократное чтение состояния вместо ожидания с повтором (прочитать count/текст/URL → сравнить).
- Ожидание не того события: ждём **отрисовку**, а зависим от **интерактивности** (гидрация SPA/SSR), ждём
  появления элемента, а зависим от завершения запроса.
- Действие, после которого нет ожидания его результата (клик → сразу чтение).
- Ожидание «сети в покое» (networkidle и аналоги) — хрупко при фоновых запросах.
- Подавленные правила линтера про ожидания (`eslint-disable`) — найти все.

### Данные и оракул
- Ассерт на порядок, который продукт не гарантирует (сортировка без tiebreaker, порядок «как вернул бэкенд»).
- Захардкоженные данные стенда (имена, id, цены, количество), абсолютные URL/хосты/локали.
- Общие тестовые данные, которые меняют другие тесты (в т.ч. параллельные воркеры).
- Зависимость от времени/даты/таймзоны/случайности без фиксации.
- Слабый ассерт, который пройдёт и при сломанном поведении (`length > 0`, `toBeTruthy`).

### Состояние и порядок
- Тест зависит от состояния, оставленного предыдущим (порядок, `beforeAll` с мутацией, глобальные переменные).
- Общая сессия/storage state/кэш браузера; warm vs cold меняет тайминги.
- Очистка (teardown) не выполняется при падении.

### Окружение и инфраструктура
- Все тесты зависят от одного setup (логин) → его сбой выглядит как массовый флейк.
- Ретраи в конфиге/CI скрывают флейк («зелёный со второго раза»), trace/артефакты пишутся только на ретрае.
- CI запускает не то, что заявлено в документации (другой набор, другие переменные окружения).
- Разные версии браузера/раннера локально и в CI.

### Документация и комментарии
- Комментарий описывает поведение, которого в коде нет (напр. «client-rendered», когда список SSR).
- «Измеренные» цифры в комментариях — проверять прогонами, не переносить в отчёт как факт.

### Playwright: что чем заменить

| Антипаттерн | Чем заменить |
|---|---|
| `page.waitForTimeout(ms)` | web-first ассерт / `waitForURL` / `waitForResponse` на результат действия |
| `expect(await loc.count()).toBe(n)`, `expect(await loc.textContent())…` | `await expect(loc).toHaveCount(n)` / `toHaveText` (повтор до таймаута) |
| `allTextContents()` сразу после действия | `await expect(loc).toHaveText([...])` или `expect.poll(() => …)` |
| `locator.waitFor()` на SSR-элемент как «страница готова» | ожидание результата действия, а не его предусловия |
| `.first()` / `.nth(i)` без гарантии порядка | уникальный локатор (test id, роль+имя) |
| `waitForLoadState('networkidle')` | ожидание конкретного ответа/состояния |
| `page.url()` + `toBe` | `await expect(page).toHaveURL(re)` |
| `retries` в конфиге для CI + `trace: 'on-first-retry'` | ретраи как сигнал (`--fail-on-flaky-tests`), а не маска |

ESLint: `eslint-plugin-playwright` — `no-wait-for-timeout`, `prefer-web-first-assertions`, `prefer-to-have-count`,
`no-networkidle`, `no-nth-methods`, `no-force-option`. Искать `eslint-disable` по всему репо.

### Формат результата
`| ID | Файл:строка | Антипаттерн | Механизм флейка | Риск (выс/сред/низ) | Активный / латентный / док-дефект | Как проверить |`

## Принудительное воспроизведение (Этап 2.2)

Цель — превратить «иногда» в «всегда при условии X». Тогда:
- гипотеза **доказана** (тест падает N/N при X и проходит без X);
- фикс проверяется **детерминированно**: при X исправленный тест проходит;
- негативная проверка строится на том же механизме.

Repro — временный эксперимент, в основной код не коммитится. Типовые условия — в
`templates/playwright/repro-conditions.ts`; разовые эксперименты сверх них — в `repro/` папки артефактов.
Запуск — через `run-condition.mjs` с `phase=repro-<гипотеза>`, 10–20 повторов достаточно (ожидаем 100%/0%).

**Условие — к настоящему тесту, не к копии.** Копия теста в `repro/` проверяет копию: после фикса её придётся
переписывать, и сравнение до/после теряет смысл. Условие включается env-переменной в переопределённой фикстуре
`page`:
```ts
page: async ({ page, baseURL }, use) => { await applyReproCondition(page, baseURL); await use(page); },
```
Правка фикстуры — локальный патч проекта: один раз внести импорт + override, `git diff <fixtures> >
.flaky/apply-repro.patch`, `git checkout <fixtures>`; дальше `git apply .flaky/apply-repro.patch` перед прогоном и
`git checkout <fixtures>` после. Так одно и то же условие гоняется против кода «до» (worktree) и «после»;
`meta.json` честно покажет `dirty` и изменённый файл.

| `REPRO_CONDITION` | Параметры | Что делает |
|---|---|---|
| `cpu` | `REPRO_CPU_RATE` (20) | CPU throttling через CDP — расширяет окно после `load` (гидрация) |
| `request-delay` | `REPRO_URL_RE`, `REPRO_DELAY_MS` (3000) | задерживает запросы, чей URL совпал с регэкспом |
| `throttled` | — | условие матрицы: CPU ×4 + ~Slow 3G |
| `gate` | `REPRO_GATE_ENV` | до теста открывает URL гейта стенда из этой env-переменной (для cold за гейтом) |

Несколько — через запятую. Конкретные `REPRO_URL_RE` проекта (JS-чанки, API после действия) — в профиле.

**Проверить, что условие действительно расширяет окно гонки**, а не сдвигает всё целиком. Признак — repro не
даёт падений там, где гипотеза их предсказывает: сначала проверить repro, потом понижать гипотезу.

**Подвох гидрации:** `page.goto()` по умолчанию ждёт `load`, а `load` ждёт и async-скрипты документа. Задержка
загрузки JS-чанков поэтому сдвигает и возврат из `goto` — окно «SSR видим, обработчиков нет» может **не**
расшириться. Окно после `load` расширяет медленное **выполнение**: CPU throttling ×10–×20
(`Emulation.setCPUThrottlingRate`). Задержка чанков работает только для чанков, загружаемых после `load`
(динамические импорты) — проверить по trace (Network vs событие load).

### Приёмы по типу причины

| Причина | Как воспроизвести |
|---|---|
| Гонка с гидрацией / загрузкой JS | `cpu` ×10–×20; `request-delay` на JS-бандлы (Next.js: `/_next/static/.+\.js(\?\|$)`, см. подвох) |
| Чтение раньше ответа/перерендера | `request-delay` на конкретный API/RSC-запрос после действия (напр. `[?&]sortBy=`), 1–3 с |
| Медленная сеть / однократное чтение | `throttled`, задержка ответа списка |
| Порядок данных (tie, нестабильная сортировка) | `scripts/list-snapshot.mjs --repeat K`: `<label>_distinct_orders` > 1 → порядок меняется между загрузками; подмена ответа с переставленными равными элементами |
| Зависимость от порядка тестов | запустить тест отдельно / после «грязного» соседа / в обратном порядке |
| Общие данные между воркерами | 2+ воркера на один и тот же тест, одни и те же данные |
| Warm/cold | `cold.config.ts` (+ `gate`) vs base |
| Захардкоженное окружение | другой base URL / локаль / таймзона |
| Время | `page.clock.install()` / `setFixedTime` на граничные значения |

Подмена ответа: `route.fulfill({ response: await route.fetch(), body: <изменённый> })`.
Признаки гидрации, которые можно ждать в repro/фиксе: смена URL/запрос после действия
(`page.waitForURL`, `page.waitForResponse`), атрибут состояния контрола (`aria-checked`/`data-state`),
web-first ассерт на результат (`expect.poll`, `toHaveText([...])`).

### Оформление (в `2-plan.md` §2)

| Гипотеза | Repro (условие, параметры) | Без X | С X | Вывод |
|---|---|---|---|---|
| H1 … | `cpu`, `REPRO_CPU_RATE=20` | 20/20 pass | 0/20 pass | доказана |

Если с X тест не падает — гипотеза понижается (не «опровергнута», если repro мог не попасть в окно — указать).
