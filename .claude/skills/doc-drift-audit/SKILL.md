# Doc drift audit: документация = код, проверено

Цель — документация, где **каждый путь, команда, версия и связь существуют в репо и проверены**, а не «правдоподобный README типичного проекта». Ответы Claude (в том числе собственные) — черновик и гипотезы, пока не сверены с кодом или запуском.

## Жёсткие правила

- **Сверка с реальностью, а не с требованием.** Источник правды — код, конфиги, запуск, официальная документация библиотек (Context7). Старый README и текст задачи могут быть устаревшими сами.
- **DRAFT до именного подтверждения.** В шапке каждого изменённого документа: `Status: DRAFT — … pending review by <имя>`. Снимается только после явного подтверждения этого человека: `Reviewed by <имя>, <дата>`.
- **Ответы Claude сохраняются дословно**, рядом — таблица сверки «утверждение → как проверено → вердикт». Наводки в промпте (подсказки из своих наблюдений) фиксируются как наводки.
- **Изменения кода — минимальные и только ради документации** (например, `engines` в `package.json`). Всё, что меняет поведение (enforce версий, CI), — на решение пользователя.
- Секреты (`.env`, ссылки стенда, storage state) не попадают ни в facts, ни в логи. URL и email маскируются.
- Без коммитов и пушей без запроса.

## Раскладка

| Слой | Где | Что |
|---|---|---|
| Скилл | `.claude/skills/doc-drift-audit/` | методика, `scripts/collect-facts.mjs`, `scripts/check-doc-refs.mjs`, `references/prompts.md` |
| Документация | `README.md`, `docs/` | `ONBOARDING.md`, `ARCHITECTURE.md`, `CHANGELOG.md` (+ `.markdownlint.jsonc`) |
| Отчёт аудита | `deliverables/docs/` (или папка из запроса) | `README`, `1-research` … `5-reflection`, `facts/`, `claude/` (дословно), `runs/` |

Если пользователь хочет только быстрый аудит без отчёта — шаги 1–2 и вывод таблицы расхождений в чат.

## Шаг 1. Research — факты рядом с документацией

```bash
node .claude/skills/doc-drift-audit/scripts/collect-facts.mjs . --out <отчёт>/facts/facts.md
node .claude/skills/doc-drift-audit/scripts/check-doc-refs.mjs . README.md > <отчёт>/runs/check-refs-before.txt
```

- `collect-facts` выдаёт: `git ls-files` (ничего не скрывать), конфиги целиком (playwright/tsconfig/eslint/.gitignore/.env.example/fixtures/CI workflow), npm-скрипты, зависимости «заявлено / установлено / engines.node», ключи `process.env`/`required()`, экспорты, `git log`. Требует установленных `node_modules`.
- Параллельно — прочитать исходники самому (pages, helpers, tests): facts показывают экспорты, но не связи между классами.
- Записать первичные наблюдения **до** запуска Claude — потом будет с чем сравнить.

## Шаг 2. Plan — расхождения и приоритеты

1. **≥2 независимых субагента** по шаблону №1 (`references/prompts.md`), вход — только старая документация + facts. Прогоны дают разные списки: объединять.
2. Каждую строку проверить: файл:строка, запуск (`npx playwright test ...` с нужными env), `--help`, Context7. Таблица сверки в `2-plan.md`.
3. Итоговый список `D1…Dn`: P1 — шаг реально не работает; P2 — вводит в заблуждение; P3 — полезно добавить. Колонки: источник (какой прогон / своё), что делаем, где.
4. Раздел «Осознанно не делаем» с причинами (например, версии инструментов в README — устаревают, источник правды `package.json`).

Типичные находки, которые стоит проверить в любом Playwright-проекте:
- заявленная версия Node против `engines` зависимостей (ESLint 9+/10, Playwright);
- какие env нужны для **любого** прогона с учётом `projects[].dependencies` (setup-проекты тянут всё);
- `--project=setup` / `--no-deps` / порядок проектов;
- правила линтера, которых нет в README (`no-focused-test`, `no-skipped-test`, `no-restricted-syntax`);
- статусы в таблицах тест-кейсов, которые читаются как «зелёный прогон».

## Шаг 3. Implement — черновик Claude → сверка → правки

- Шаблоны №2–5 (`references/prompts.md`) — свежий субагент на каждый документ, ответ дословно в `claude/0N-*.md`. Субагенты можно запускать параллельно; **не править входные файлы, пока они читают**.
- Просить у Claude TODO вместо догадок и пометку *(inferred)* — это делает ошибки дешёвыми для поимки.
- Сверка — по таблице «предложение Claude → проверка → решение (принято / изменено / отклонено)» в `3-implement.md`. Проверять **и свой текст**: ошибки человека ловятся тем же способом.
- ARCHITECTURE: только существующие слои (явно написать, чего нет), реальные классы и переходы, mermaid + текстовое описание, раздел «куда добавлять новое».
- CHANGELOG: от новых к старым; смена **смысла** env-переменных и способа запуска важнее новых файлов; секция «Unreleased» для текущей ветки.

## Шаг 4. Verify

1. **Чистый клон** в scratchpad (+ наложить незакоммиченные изменения), пройти ONBOARDING **дословно**, лог в `runs/`. Сравнить каждое «you should see …» с фактом. CLI-флаги вроде `--reporter` меняют поведение — прогонять ровно команды из гайда.
2. Негативные сценарии из Troubleshooting — воспроизвести (например, пустые admin-креды).
3. `check-doc-refs.mjs` по README + `docs/` → 0 errors; контрольно на старом README — ошибка всё ещё ловится.
4. Mermaid — отрендерить (Playwright + mermaid ESM из CDN) и посмотреть картинку.
5. Явно перечислить, что не проверено и почему (нет нужной версии Node, браузер в кэше, CI не запускался).
6. Таблица именного подтверждения; после «подтверждаю» — снять DRAFT.

## Шаг 5. Reflection

Что Claude нашёл / пропустил / додумал (с примерами), что поймала сверка в собственном тексте, какие доработки скилла дал прогон, как запускать регулярно (перед релизом, раз в спринт, после PR, меняющего конфиг/CI/env).

## Регулярный запуск

Короткий цикл (≈15 мин): `collect-facts` → 2 субагента по шаблону №1 → сверка → `check-doc-refs` → правки только P1/P2 → DRAFT → ревьюер. Полный цикл с ONBOARDING на чистом клоне — при смене Node/Playwright/ESLint, env-переменных, проектов конфига или CI.
