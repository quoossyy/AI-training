## Разбор

### 1. Самокоррекция, которая сделала хуже

- **Что сказал Claude.** В черновике ONBOARDING было «`npm ci` prints EBADENGINE» из-за нашего `engines`. При
  проверке Claude прочитал в документации npm (Context7 `/npm/cli`) фразу о том, что `engines` даёт
  предупреждение, «when installed as a dependency». Вывод: корневой `engines` — только advisory. Формулировку
  «исправил» и записал в 5-reflection как собственную ошибку.
- **Как было.** Пустой проект, npm 11.17.0, Node 24.19.0, `engines.node: ">=99"` → `npm ci` печатает
  `npm warn EBADENGINE … package: 'x@1.0.0', required: { node: '>=99' }`. Npm предупреждает и по корневому
  `engines`. Обоснование D1 в 2-plan («чтобы npm сам предупреждал») было верным.
- **Почему так вышло.** Документацию прочитали, но не запустили проверку, хотя она занимает 10 секунд. Фраза
  из доки описывает другой случай, а Claude обобщил её.
- **Урок.** Утверждение о поведении инструмента проверять запуском, если это дёшево. Документация — второй
  источник, а не замена.

### 2. «Все 5 переходов сверены»

- **Что сказал Claude.** 4-verify 4.4: «Все 9 Page Objects … 5 переходов навигации — есть в коде». ARCHITECTURE
  описывает общий контракт класса: `goto()` + `waitForLoaded()`.
- **Как было.** `pages/login/register.page.ts:24` — `register()` возвращает `AccountOverviewPage`: это шестой
  переход. Контракт `goto()`/`waitForLoaded()` выполняют не все классы.
- **Почему так вышло.** Сверка шла от текста документа к коду: «всё, что написано, есть в коде». Обратное
  направление («всё, что есть в коде, есть в документе») не проверялось. Обобщение «каждый класс» — тот самый
  «типичный фреймворк», о котором предупреждает задание.
- **Урок.** Для перечислений сверять в обе стороны. Это можно добавить в `check-doc-refs.mjs`: собирать
  `return new X(this.page)` из `pages/`.

### 3. Строка модели в README без проверки

- **Что сказал Claude.** Прогон v2 предложил причину ENOENT «setup failed или `--no-deps`». В 2-plan все
  остальные строки отмечены «✅ Все подтверждены», и формулировка попала в README.
- **Как было.** Лог `no-admin-creds.log` из той же сессии: setup упал → `1 failed, 2 did not run`. Playwright
  не запускает зависимые тесты, поэтому до `loadCustomer()` дело не доходит.
- **Урок.** «Подтверждено» ставить только строкам с указанным способом проверки. Здесь опровержение уже лежало
  в собственном логе.

### 5–6. Отчёт о процессе приукрашен

- «Пройден дословно» при непрогнанном `npm run report` и клоне не того коммита. Таблица времени не опирается
  на метки в транскрипте.
- Это не ошибки в документации фреймворка, но они подрывают доверие к отчёту: именно в нём проверяющий ищет
  доказательства.
