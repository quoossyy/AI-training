## 1. Критерии

**Flaky** = тот же коммит, то же окружение, тот же тест → pass и fail **по одной и той же целевой причине**.
Падения setup (логин админа, session link) и сети — **шум окружения**, считаются отдельно. Комментарии в коде
(«passes ~40%») не считаются данными; класс определяется только по прогонам.

| Исход N прогонов (`--retries=0`) | Класс | Действие |
|---|---|---|
| все pass | `stable-pass` — стабилен **или латентный** | стресс-условия (волна 3) |
| ни одного pass | `always-fail` — детерминированное падение, **не flaky** | разбор как обычного падения |
| есть pass и fail (целевая причина) | `FLAKY` | гипотезы → repro → фикс |
| падения только из-за шума | `stable-pass (env noise)` / `noise-only` | в отчёт, тест не чиним |

**Почему 10 прогонов мало для «стабилен».** 0 падений из N → реальная частота до ≈ 3/N («правило трёх», 95%):
10 → до ~30%, 20 → до ~15%, 30 → до ~10%. Поэтому обнаружение — 20 повторов на условие, «починен» — 0 целевых
падений из 30 в каждом обязательном условии + проходит repro + падает в негативной проверке.

Git Bash, из корня репо. Сначала — блок «Определения команд» из [профиля](../../.flaky/profile.md)
(`$SK`, `$RC`, `$SNAP`, `${META[@]}`, `${PW[@]}`).

```bash

time npx playwright test --project=flaky --retries=0 --reporter=list

# Волна 1
$RC before base "${META[@]}" -- "${PW[@]}" --project=flaky --repeat-each 20 --workers=1

# Волна 2 (флейки/подозрительные; пример для STORE-02)
$RC before parallel "${META[@]}" -- "${PW[@]}" --project=flaky --repeat-each 20 --workers=4 --fully-parallel

git apply .flaky/apply-repro.patch   # cold за гейтом стенда: условие gate открывает SESSION_LINK
REPRO_CONDITION=gate REPRO_GATE_ENV=SESSION_LINK $RC before cold "${META[@]}" -- "${PW[@]}" -c $SK/templates/playwright/cold.config.ts --project=flaky-cold --repeat-each 20 --workers=1
git checkout -- fixtures/index.ts
$RC before retries "${META[@]}" -- npx playwright test --project=flaky --retries=2 --reporter=list,json --repeat-each 10

# Волна 3 (кандидаты в латентные)
git apply .flaky/apply-repro.patch
REPRO_CONDITION=throttled $RC before throttled "${META[@]}" -- "${PW[@]}" --project=flaky --repeat-each 20 --workers=1
git checkout -- fixtures/index.ts

# Статистика
node $SK/scripts/flaky-stats.mjs --out deliverables/flaky/runs/stats.md deliverables/flaky/runs
```

После каждого прогона с падениями сразу сохранить нужные `test-results/**/trace.zip` в `runs/_local/` (не

## 4. Успешный vs неуспешный прогон (артефакт b)

### Промпт — шаблон №2 «Сравнение прогонов», адаптирован

> Сравни два trace STORE-02 с одного коммита (`dee3b18`) и одного условия: успешный и упавший. По шагам
> (клик → запрос сортировки → ответ → чтение списка → ассерт) выпиши время относительно начала клика, что было
> в DOM на шаге чтения и какие сетевые запросы были. Назови различие, которое определяет исход, и скажи, какие
> гипотезы H1–H6 оно подтверждает или опровергает. Фиксы не предлагай.

**Наблюдения → выводы:**

- Клик срабатывает во всех случаях: запрос сортировки отправлен и в успешном, и в упавших прогонах (и во всех
  55 проверенных падениях, §3). **H1 опровергается** для этого стенда.
- Исход определяется только тем, **что раньше: ответ сортировки или однократное чтение**. Без нагрузки чтение
  всегда раньше: ответу нужно ~100 мс, чтению после клика — ~5 мс. Отсюда 100% падений. Под CPU ×20 клик
  растягивается до ~1.5 с, и иногда ответ успевает прийти и отрисоваться до чтения. Отсюда редкие проходы
  (5/50). **H2 подтверждается**, затем доказана repro ([2-plan.md](2-plan.md)).
- В успешном trace есть ещё три запроса `sortBy` (2767 мс). Это, вероятно, предзагрузка ссылок после перерендера
  (не проверялось). На исход они не влияют: приходят после завершения чтения.
- Порядок после применённой сортировки — T-Shirt первым, как и при прямой загрузке (H3 не причина, H6
  опровергнута).

**латентные** дефекты. Их нельзя «починить по статистике», потому что статистика зелёная. Ниже — что их
объединяет со STORE-02.

**Общий корень: тест проверяет состояние, которое случайно совпало с ожидаемым, а не то, которое продукт
гарантирует, и проверяет его однократным чтением.** STORE-02 — тот же дефект в активной форме: однократное
чтение после действия всегда опаздывает.

| Тест | Риск | В чём совпадение со STORE-02 | Почему зелёный сейчас | Замена |
|---|---|---|---|---|
| STORE-01 | R-13 | ассерт на позицию в порядке, который UI не обещает (как «T-Shirt первый» при равных ценах) | порядок по умолчанию стабилен (снимок ×20) | проверять набор (`arrayContaining`) или явно заданный порядок |
| STORE-03 | R-14 | однократное `count()` вместо retrying-ассерта | список SSR, 4 карточки уже в HTML | `await expect(storePage.productCards).toHaveCount(4)` — линтер уже предупреждает (`prefer-to-have-count`) |
| STORE-04 | R-15 | синхронизация фиксированной задержкой + однократное чтение + слабый ассерт `length > 0` | SSR: цены есть в HTML ещё до `waitForTimeout(150)` | `toHaveCount(4)` на ценах, затем проверка значений; убрать `eslint-disable` |
| STORE-05 | R-16 | однократное `page.url()` + захардкоженный хост | `BASE_URL` совпадает с захардкоженным | `await expect(page).toHaveURL(/\/dk\/store$/)` |

**Правило для набора:** после любого действия ждать его наблюдаемый результат (URL, ответ, web-first ассерт на
итоговое состояние), а не отрисовку и не время. В ассерте проверять то, что продукт гарантирует. Проверить
латентные дефекты так и не удалось: условие throttled оказалось невалидным (§3). Нужен откалиброванный пресет
или смена данных (новый товар, другой `BASE_URL`), это следующий шаг, если STORE-01/03/04/05 возьмут в работу.
