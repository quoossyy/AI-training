### Почему это устраняет причину, а не симптом

- **Ждём результат действия, а не отрисовку.** `sortBy()` возвращается, только когда клик сработал: URL
  сменился (смена URL через History API для Playwright — навигация, `waitForURL` её ловит; проверено по
  документации Playwright 1.63 через Context7). Это ожидание события, а не фиксированной задержки.
- **Retrying-ассерт вместо однократного чтения.** `toHaveText` на первом заголовке перечитывает DOM до
  появления отсортированного списка — гонка «чтение vs перерендер» закрыта, сколько бы ни шёл ответ (repro +3 с —
  10/10 pass). Таймауты не менялись (дефолтные 5 с ассерта / 30 с теста).
- **Ассерт не ослаблен, а усилен.** Сохранена исходная проверка «T-Shirt первый», добавлены: сортировка
  применена (`sortBy=price_desc` в URL) и цены по невозрастанию — то, что сортировка по цене действительно
  гарантирует. Сейчас все цены равны, и последняя проверка тривиальна; она начнёт ловить ошибки, как только
  в каталоге появятся разные цены. Чтобы она не проходила «пусто», 06.11 добавлено: цен больше одной и каждая —
  положительное число (`toEqual` считает `NaN` равным `NaN`, а пустой массив «отсортирован» всегда).
- **Диагностика при поломке.** Клик без эффекта → падение в `sortBy()` с `page.waitForURL` (строка сортировки);
  неверный порядок → `toHaveText` с `Expected "Medusa T-Shirt" / Received "…"`. Обе ветки проверены
  негативными проверками ([4-verify.md §3](4-verify.md#3-проверки)).

### Остаточная причина (H7): ответ сортировки пришёл, но не применён

Повторный замер 2026-11-06 (независимая перепроверка, [4-verify.md §2.1](4-verify.md#21-повторный-замер-2026-11-06-перепроверка)):

- **Записано в `runs/`:** 350 прогонов «после» (05.11 — 90, 06.11 — 260), **8 падений (2,3%, 95%-интервал
  ≈1–4,5%)**. Все 8 — `page.waitForURL: Test timeout of 30000ms` в `sortBy()`, все 8 разобраны по trace — H7.
  Сигнатура H2 (`toBe … Received "Medusa Sweatshirt"`) после фикса — **0 раз**.
- **Без отчёта:** ещё 25 прогонов с 4 падениями — 1/10 в первом прогоне перепроверки (`--reporter=line`,
  сигнатура неизвестна), 1/5 в быстрой проверке после правки ассертов (`waitForURL`, по `error-context.md`),
  2/10 в прогоне агента-проверяющего (`waitForURL`, по его отчёту).
- **Частота неравномерная:** 0/90 05.11; по сериям 06.11 — от 0/30 до 3/40, 2/10, 1/5; на итоговом коде
  (блоки 10–12) — 3/60. Оценка: **~2–5%**.

Разбор trace — одинаковый во всех 9 разобранных падениях (8 обычных + 1 под repro; trace локально в
`runs/_local/after/2026-11-06_traces/`):

| Признак | Что в trace |
|---|---|
| Страница гидрирована до клика | `Link` уже сделали prefetch (`/dk/cart?_rsc=…`, `/dk/products/*?_rsc=…`) — React подключён |
| Клик сработал | ушёл навигационный RSC-запрос `/dk/store?sortBy=price_desc&_rsc=…` (без заголовка `next-router-prefetch`) |
| Сервер ответил | **200** за 61–341 мс |
| Результат | URL остался `/dk/store`, список 30 с в порядке по умолчанию (Sweatshirt первый, T-Shirt последний) — снимок `error-context.md` |
| Консоль | `Mixed Content … http://medusa-backend:9000/store/product-options…` → `Failed to fetch product options`. **Не различает:** та же ошибка в 5/5 проходящих trace (`--trace on`). Это отдельный дефект конфигурации стенда (клиенту отдан внутренний адрес бэкенда) |

Механизм не установлен. Попытки принудительного воспроизведения на фиксе (условие должно давать ~N/N):

| Условие | Идея | Результат |
|---|---|---|
| prefetch-RSC +2 с (`REPRO_URL_RE='^(?!.*sortBy=).*[?&]_rsc='`) | навигация теряется, когда в полёте prefetch | 10/10 pass |
| prefetch-RSC +150 мс | ответы prefetch приходят сразу после ответа сортировки | 10/10 pass |
| JS-чанки +300 мс (`/_next/static/chunks/`) | догрузка чанков во время навигации | 9/10 pass (1 — та же сигнатура, на уровне фона) |
| CPU ×4 / CPU ×2 | конкуренция за CPU, как в parallel | 20/20 / 20/20 pass |

От числа воркеров частота заметно не зависит (1 воркер — 4/160 записанных, 4 воркера — 4/160). Гипотезы о
триггере (prefetch, чанки, CPU) не подтвердились.

**Чем H7 не является:** не H2 (ответ пришёл, но список не изменился за 30 с — дело не в раннем чтении), не H1 в
форме «клик проглочен» (запрос ушёл), не дефект сервера (ответ 200, прямая загрузка `?sortBy=` стабильна — H6).
Остаётся клиент: ответ навигации получен, но не применён. Связь с гидрацией/роутером Next.js — предположение.

**Почему фикс не трогаем:** тест ждёт наблюдаемый результат действия и падает в правильном месте с понятной
сигнатурой. Повторный клик, ретрай или больший таймаут скрыли бы дефект, который видит пользователь (нажал
сортировку — ничего не произошло, хотя запрос прошёл). Это ровно то, что разделение `waitForURL` в `sortBy()` и
`toHaveText` в спеке должно было различать.

### Отличие от эталона в `FLAKY-TESTS.md`

Эталон: `await expect.poll(() => storePage.productNames().then(n => n[0])).toBe('Medusa T-Shirt')`.

- **Причина в эталоне названа неверно для этого стенда.** `FLAKY-TESTS.md` и комментарий теста объясняют
  флейк гидрацией («клик до React теряется, запроса нет»). На стенде запрос сортировки был в 55/55
  падениях «до» и в 9/9 разобранных «после» — «запроса нет» не наблюдалось ни разу. Основная причина —
  однократное чтение до ответа (R-02 в карте рисков; в комментарии теста не названа). Остаток (H7) — навигация,
  которая отправлена, но не применена; связана ли она с гидрацией, не установлено.
- **Частота другая.** Эталон: ~40–60% pass warm, ~87% pass cold. Измерено: **0/110 pass** во всех обычных условиях;
  флейк (5/50 pass) появляется только под CPU ×20. На этой машине и стенде тест не «флейкал», а падал
  детерминированно — та же гонка с другим исходом.
- **Эталон тоже устранил бы гонку** (`expect.poll` перечитывает), но:
  - при клике без эффекта он падает с «`Received: Medusa Sweatshirt`» — неотличимо от сломанной сортировки;
    фикс разводит эти случаи (`waitForURL` в `sortBy()` vs `toHaveText`);
  - он оставляет тест привязанным к tie-break при равных ценах (R-03) и не проверяет, что сортировка по цене
    вообще соблюдена; фикс добавляет проверки URL и порядка цен;
  - ожидание результата действия живёт в Page Object (конвенция профиля «PO ждут свои состояния»), а не в
    каждом тесте, который сортирует.
