# 2. Plan — гипотезы и их доказательство (STORE-02)

> Черновик по статике, до прогонов. Порядок — по априорной вероятности; пересматривается после прогонов «до» и
> сравнения pass/fail ([1-research.md](1-research.md)). R-xx — риски из карты рисков там же.

## Промпт — шаблон №2, адаптирован

> На основе карты рисков и кода STORE-02 составь список гипотез причины нестабильности в порядке
> вероятности. Для каждой: механизм, какой наблюдаемый признак в trace/логе её подтверждает или опровергает,
> минимальный эксперимент для **принудительного воспроизведения**. Не предлагай фиксов. Не предлагай увеличивать
> таймауты или добавлять ретраи.

## 1. Гипотезы

| # | Гипотеза | Риск | Подтверждает | Опровергает |
|---|---|---|---|---|
| H1 | **Клик до гидрации теряется.** Радио сортировки из SSR видимо, обработчик React ещё не подключён | R-01 | В trace fail после `click` **нет** смены URL на `sortBy=price_desc` и нет RSC-запроса | После клика URL меняется в каждом падающем прогоне |
| H2 | **Чтение раньше перерендера.** Клик дошёл, но `allTextContents()` выполнилось до прихода отсортированного списка | R-02 | В trace fail URL сменился, **но** снимок DOM на шаге чтения ещё в старом порядке | Порядок в DOM уже новый на момент чтения |
| H3 | **Оракул неверен: tie при равных ценах.** Все товары €10.00; порядок задаётся порядком ответа/алгоритмом сортировки | R-03 | Сортировка **применена** (URL, радио отмечено), а `names[0]` ≠ T-Shirt; или порядок `price_desc` меняется между загрузками | При применённой сортировке порядок всегда один и T-Shirt первый |
| H4 | **Warm-сессия меняет тайминг.** `storageState` админа / кэш → другое соотношение «гидрация vs клик» | R-06 | Частота падений warm ≠ cold сверх статистического шума | Частоты совпадают |
| H5 | **Нагрузка/параллельность** удлиняет окно до гидрации | R-01 | `--workers=4 --fully-parallel` / throttling заметно повышают частоту | Частота не зависит от нагрузки |
| H6 | **Дефект продукта:** сервер иногда игнорирует `sortBy` | — | Прямая загрузка `/dk/store?sortBy=price_desc` (без клика) даёт разный порядок / не T-Shirt первым | K прямых загрузок дают один порядок с T-Shirt первым |

H1 и H2 не взаимоисключающие: оба дают «список не отсортирован», различаются только тем, дошёл ли клик.
H3 ортогональна им: даже после устранения H1+H2 тест может остаться неверным по смыслу.

## 2. Принудительное воспроизведение

Условие включается переменной `REPRO_CONDITION` в фикстуре `page` (шаблон скилла
`.claude/skills/flaky-tests/templates/playwright/repro-conditions.ts`) через локальный патч `.flaky/apply-repro.patch`.
Под условием гоняется **настоящий** `tests/store/store.spec.ts`; тот же механизм затем проверяет фикс и негативную
проверку. Патч не коммитится; `meta.json` фиксирует `dirty`.

Определения `$RC`, `$SNAP`, `${META[@]}`, `${PW[@]}` — в [профиле](../../.flaky/profile.md), параметры условий
(`REPRO_URL_RE` и т.д.) — там же, «Throttled / repro».

```bash
git apply .flaky/apply-repro.patch
REPRO_CONDITION=<условие> [REPRO_URL_RE=<RE>] $RC repro-<h> <условие> "${META[@]}" -- "${PW[@]}" \
  --project=flaky --grep "STORE-02:" --repeat-each 10 --workers=1
git checkout -- fixtures/index.ts
```

| Гипотеза | Условие | Ожидание, если гипотеза верна | Результат |
|---|---|---|---|
| H1 | `cpu` (`REPRO_CPU_RATE=20`, CPU ×20 после `load`) | STORE-02 падает ~10/10; в trace после клика нет смены URL | _—_ |
| H1 (альт.) | `request-delay`, `REPRO_URL_RE='/_next/static/.+\.js(\?\|$)'` | ⚠ может **не** сработать: `goto()` ждёт `load`, а он ждёт и async-чанки — окно сдвигается целиком. Не воспроизвелось ≠ опровергнуто | _—_ |
| H2 | `request-delay`, `REPRO_URL_RE='[?&]sortBy='` (3 с) | ~10/10; в trace URL уже `sortBy=price_desc`, DOM на шаге чтения — старый порядок | _—_ |
| H3 | без патча: `$SNAP --repeat 20` (`list-snapshot.mjs`, см. профиль) | цены равны; порядок `price_desc` меняется между загрузками или определяется не ценой | _—_ |
| H4 | cold (`$SK/templates/playwright/cold.config.ts` + `gate`) vs base | разная частота при одинаковом N | _—_ |
| H5 | `throttled` / `--workers=4 --fully-parallel` | рост частоты | _—_ |
| H6 | `$SNAP --repeat 20` (прямые загрузки) | разные порядки / T-Shirt не первый | _—_ |

«При условии X тест падает N/N» → гипотеза **доказана**; не воспроизводится → гипотеза понижается (с учётом
ограничений repro), берётся следующая.

## 3. Логика вывода «тест или продукт»

- H1 и/или H2 доказаны, H6 опровергнута → **проблема в тесте**: ждём отрисовку вместо результата действия.
- H3 подтверждена → проблема **в тесте (оракул)** и **в данных стенда**: при равных ценах сортировку по цене
  проверить нельзя. Тест должен проверять гарантированное (сортировка применена; цены по невозрастанию), а вопрос
  «нужны товары с разными ценами / tiebreaker» — команде. Это не дефект продукта, пока продукт не обещает tiebreaker.
- H6 подтверждена → дефект продукта; тест прав (после устранения H1/H2).

## 4. План фикса

_После доказательства причины: что меняем (PO / спека), почему это убирает причину, как проверим под repro._
